The shipped Dock `main.qml` and skeleton `kwinrc` are byte-identical between the two ISOs. Their package versions and compositor versions differ; identical configuration does not prove identical rendering/timing. NiceC0re's Dock pins `seafari.desktop` and `pearos-appstore.desktop`, whereas Goldwing pins the preferred browser and GNOME Software.

Seafari's desktop launcher executes `/usr/bin/seafari`, a shell wrapper that copies its CSS theme into `~/.mozilla/seafari-profile`, writes UI/search/start-page preferences, and starts the packaged Firefox binary with a dedicated profile/name. We read the wrapper without executing it. The shipped `seafari.cfg` contains new-tab/window, bookmark/history/download commands and the global-menu preference/injection code seen in the source. Static code presence does not establish working DBus menu export. No user-agent override was found in the selected `seafari.cfg`, launcher or policies; runtime user-agent behavior is untested.

The shipped policies explicitly set `DisableAppUpdate=true`, `app.update.auto=false`, and `app.update.enabled=false`; `AppUpdateURL` points to `https://apt.inled.es`. The same policies request `extensions.webextensions.remote=false` and `browser.tabs.remote.autostart=false`. These are observed settings, not proof of their runtime effect in this Firefox version. Distro package updates may replace Seafari independently; their freshness and delivery were not verified. Do not carry these settings into makOS without reviewing the update and process-isolation behavior.

Selected files and SHA-256 values are in `selected-artifacts.json`. REA target-free ELF evidence for shipped `firefox-bin` is retained as `rea-seafari-elf.json`: x86-64, 639,792 bytes, SHA-256 `33ffc3bfbd0575fa497d810b16ba85a78ddc9736be0fd8140a2d3a4e36516bf5`, GNU build ID `15aeea801de5a7ef4f8a70dba83fefdbe21618d7`. As with Pafari, the ELF notes establish identity, not runtime functionality or engine maintenance.

## Pafari and Seafari

| | Pafari | Seafari |
| --- | --- | --- |
| Source identity | [pearOS-archlinux/pafari](https://github.com/pearOS-archlinux/pafari/tree/278b8980e78da9abc3ab0a34ff9c1ccc59e500b0) | [InledGroup/seafari](https://github.com/InledGroup/seafari/tree/48469ff687c8c84b83d27322d12ecb11c56c2bd4) |
| Mechanism verified in code | Epiphany fork: C, GTK4, libadwaita, `webkitgtk-6.0` | Downloads Mozilla Firefox binaries, patches `omni.ja`, branding, CSS, privileged autoconfig; packages result |
| Browser engine | WebKitGTK | Firefox/Gecko |
| UI technology | GTK/libadwaita | Firefox browser chrome/XUL/CSS/JavaScript |
| Observed ISO inclusion | Goldwing 26.8-1; absent from NiceC0re package records | NiceC0re 2.5.8-1; absent from Goldwing package records |
| Existing functionality in source | Epiphany bookmarks/download management, tabs, incognito mode | Firefox browser facilities retained; injected menu commands for tabs, windows, bookmarks, history, downloads |
| Global menu | Needs runtime verification | Source and shipped `seafari.cfg` build XUL menubar and enable GTK/portal menu preferences. This is an attempted integration, not yet a verified working DBus export |
| Packaging | Native application with Meson, Arch PKGBUILD and Debian build recipe | `.deb`, `.pkg.tar.zst`, `.rpm`, AppImage |
| License observations | Meson declares GPL3+, COPYING present | Packaging declares MPL-2.0; no top-level LICENSE observed in selected source checkout, so audit custom assets/modification licensing before copying |

Neither can be substituted directly for a Qt Quick `WebEngineView`. Pafari needs a GTK application or deliberate WebKitGTK integration. Seafari is a complete Firefox-derived application, suitable to launch as its own Wayland window and customize; it is not an embeddable Qt browser backend. For production browsing, retaining an upstream-maintained browser engine and a bounded UI patch set is preferable to rewriting browser internals. This is a design recommendation, not a claim that either fork is already validated for makOS.

Seafari's build defaults `SAFARI_UA=false`; Safari user-agent spoofing is an explicit `--safari-ua` option in the source. The selected shipped configuration has no such override. Source README claims daily updates, but this does not establish an installed update mechanism; the actual shipped policies above disable the in-app updater.

## Reuse decision

Keep Deepin/Treeland as the makOS base. Reuse the Pear work selectively: native-menu data flow, Dock layout/geometry publication, minimize deformation concepts, and app UI references. A wholesale Pear Dock or Liquid Gel install would pull in Plasma/KWin and conflict with the chosen shell/compositor architecture.

The selected source uses GPL-family licenses (Dock GPL-2.0-or-later; Liquid Gel GPL-2.0-or-later; Magic Lamp GPL-2.0-or-later; appmenu file SPDX GPL-2.0-only OR GPL-3.0-only OR KDE-accepted alternatives; Pafari GPL3+). Preserve upstream attribution and inspect per-file and asset licenses if actually importing code. No source import has occurred here.

The inspected Pear Notes/Contacts/Calendar implementations persist `notes.json`, `contacts.json`, and `events.json` through Qt JSON storage. Their presence does not imply mail/calendar/contact account integration. Keeping our existing SQLite data model until a concrete missing capability is identified avoids an unjustified backend replacement.

The Pear Settings source is Qt6/QML, but many settings use `QProcess` with `nmcli`, `pactl`, `kscreen-doctor` and D-Bus/UPower commands. The visual pages are useful references; this is not a compositor-neutral settings service. Network/audio/account capabilities should connect to the chosen makOS system services, and display/workspace controls must target Treeland. Replacing our frontend with this app would still require backend integration and runtime testing.
